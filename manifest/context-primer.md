# SiteForge Context Primer

## What SiteForge Is

SiteForge is NOT:
- a website builder
- a generic CMS
- a form generator
- a page builder
- a theme engine

SiteForge IS:
# an intelligence-driven digital production system.

The website is only the final artifact of a larger intelligence pipeline.

---

# Core Operational Philosophy

The Factory operates through layered orchestration:

Recon → Intelligence → Strategy → Build Contract → Astro Rendering → Deployment → Lifecycle Updates

Each layer has distinct responsibilities.

The system must remain:
- modular
- deterministic
- intelligence-driven
- strategy-first
- render-safe

---

# Core Architectural Rules

## Rule 1 — Recon Drives Strategy
The system does NOT start with components.

The system starts with:
- market intelligence
- competitor analysis
- opportunity analysis
- emotional positioning
- trust analysis
- AEO analysis

Recon determines:
- positioning
- vibe
- layout direction
- conversion strategy
- trust strategy
- intake priorities

---

## Rule 2 — Strategy Drives Build
Components do NOT determine requirements.

Strategy determines:
- section priorities
- trust density
- proof requirements
- gallery importance
- CTA structure
- emotional pacing
- layout hierarchy

The build contract is assembled FROM strategy.

---

## Rule 3 — Astro Consumes ONLY site.json
Astro components must consume ONLY:
- normalized
- validated
- deterministic
- render-safe data

Astro must NEVER consume:
- recon intelligence
- intake scratch state
- AI reasoning
- strategic notes
- unresolved inference

---

## Rule 4 — Components Are Presentation-Only
Astro components should:
- render finalized decisions
- remain deterministic
- avoid business logic
- avoid orchestration logic

Components must NEVER:
- determine strategy
- determine readiness
- infer positioning
- infer layout priorities

---

## Rule 5 — No Hardcoded Industries
The Factory is horizontal infrastructure.

No:
- niche-specific branching
- keyword-specific logic
- industry templates
- hardcoded assumptions

The system must infer dynamically from:
- recon
- strategy
- market conditions
- business model
- emotional positioning

---

## Rule 6 — Readiness Is Strategic
Readiness is NOT:
- field completion
- arbitrary checklists
- component satisfaction

Readiness IS:
- positioning readiness
- trust readiness
- conversion readiness
- visual readiness
- offer readiness
- service readiness
- contact readiness

---

## Rule 7 — AI Performs Reasoning, Not Rendering
AI is responsible for:
- analysis
- synthesis
- prioritization
- positioning
- strategy
- recommendations

AI is NOT responsible for:
- frontend rendering
- deterministic layouts
- component logic
- schema enforcement

---

## Rule 8 — The Human Report Is NOT The Product
The free recon report exists to:
- demonstrate expertise
- create urgency
- build trust
- expose opportunity

The real product is:
- strategy
- orchestration
- execution
- lifecycle optimization

---

## Rule 9 — GitHub Is The Factory Memory
GitHub stores:
- contracts
- intelligence snapshots
- client state
- assets
- deployment history
- operational history

GitHub Actions orchestrates the Factory lifecycle.

---

## Rule 10 — The Factory Must Protect Quality
All builds should eventually enforce:
- Lighthouse thresholds
- schema validation
- accessibility
- AEO readiness
- answerability
- performance quality

The Factory should reject low-quality outputs automatically.
